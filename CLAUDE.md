## 5. Workflow B — How It Actually Works

Full detail in `WORKFLOW_B.md`. Summary for quick reference:

```
STEP 1 — Ravi brings raw inputs, Claude Code drafts content
  Ravi provides:
    • RA report (PDF)              ← mandatory
    • Drawing files                ← mandatory
    • Site photos                  ← mandatory
    • Questionnaire answers        ← fill what you have (4 standard forms)
    • ChatGPT section_outline.yaml ← OPTIONAL skeleton, use if available

  Claude Code:
    → reads all inputs
    → asks gap questions in ONE batch (not one at a time)
    → confirms tier (A / B / C)
    → drafts all section content
    → produces machine_data.json + section_content.yaml

STEP 2 — Ravi reviews and approves both files
  No .docx is generated until Ravi gives approval.

STEP 3 — Claude Code generates .docx + .xlsx
  Pure code execution — no LLM drafting at this stage.

STEP 4 — Compliance review
  Fix any issues in source files → regenerate.
  Never patch the .docx directly.
```

**The 4 standard intake questionnaire forms** (Ravi fills what is available, rest stays blank):

| Form                       | Key data it covers                                                         |
|----------------------------|----------------------------------------------------------------------------|
| Machine Data               | Name, model, serial, year, power, voltage, air pressure, PLC/HMI, cycle time, stations, operator count |
| Documents & Drawings       | Which docs exist: RA ✅, schematics ✅/partial/❌, PLC backup, HMI alarm list, SOP, OEM manual |
| Safety & Operation Inputs  | LOTO points, safety devices, guarding, PPE, startup/shutdown procedures, maintenance details, operator interview notes |
| Site Photographs Checklist | Which photos were taken: full machine views, control panel, e-stop, LOTO isolators, hazard zones, nameplate |

## 7. Technical Stack & Code Conventions

- **Word generation:** Node.js `docx` library v9.6.1 — each section as a standalone `.js` file
- **Excel generation:** Python `openpyxl`
- **Validation:** run after every section injection:
  `python3 /mnt/skills/public/docx/scripts/office/validate.py`
- **Working directory:** `Projects/Pxx-name/working/`
- **Final outputs:** `Projects/Pxx-name/outputs/`

### Code Gotchas — Do Not Re-Learn These

1. **Never use `str_replace` for Unicode content.** Em-dashes and special symbols cause silent
   failures. Use Python `content.replace(placeholder, new_code)` injection instead.
2. **`PageNumber.CURRENT` goes inside a `TextRun` children array** — never `new PageNumber()`.
3. **Extend `bodyChildren` explicitly** when adding sections beyond the original stub count.
   Sections 11–13 and Appendices break silently if this is missed.
4. **TOC is a Word field** — Ravi must refresh it manually after opening:
   right-click → Update Field → Update entire table. Always note this on delivery.
5. **Sections 8–10 can be one `.js` file** — inject via the Section 10 placeholder.
6. **Fix in source, regenerate** — never patch the generated `.docx` directly.

## 8. Non-Negotiable Content Rules

Firm rules from hard-won project experience. Any violation is a defect.

### Identity & Attribution
- Author/role field everywhere: **"Certified Safety Professional"** — no individual name, ever
- Never write "B11 LMSS" or any variant in any customer-facing document
- Never name SICK India or any RA firm — use **"Independent Safety Consultant"**
  and **"Machine Safety Assessment"** instead

### Document Structure
- **13 sections + 2 appendices only.**
  Appendix A = Maintenance Log Template. Appendix B = LOTO Log Template. Nothing else.
- **Appendix A (Residual Risk Summary) permanently removed.** Never regenerate it.
- **TOC: H1 entries only, single instance** on pages 3–4. Never repeated.
- **Revision table: 4 columns only** — Revision / Date / Description / Reviewed By.
  No "Prepared By" column.
- **Liability disclaimer: Section 13 only.** Never in Section 1. Never duplicated.
- **Sign-off blocks: once only**, at end of Section 13.
- **Sec 1.6 and Sec 13.3: role only** — no individual name.
- **Section 3: max 2 pages, narrative paragraphs only.**
  No tables. No boxes. No hazard register table.
  End with reference to Machine Safety Assessment Report.

### Boxes & Flowcharts
- **No DANGER boxes anywhere.** Zero exceptions.
- **Flowcharts only** (no prose, no tables) for:
  sections 4.4, 4.5, 5.4, 5.5, 6.4, 6.5, 6.7, 6.8, 6.9, 11.4, 12.2
- Flowchart style: borders `#1F3864`, white fill, pill terminals,
  ≤10 steps, ≤10 words per step, greyscale-readable.

### Open Actions Register
- **Always a standalone `.xlsx`** — never inside the manual.
- 7 columns: ID / Description / Category / Priority / Responsibility / Target Date / Status
- Filename: `[Client]_[MachineName]_OpenActions_V1.0.xlsx`

### Compliance Standards
- **In use:** ISO 12100:2010, ISO 20607:2019, IEC 82079-1:2019, IS 4571:2008,
  ISO 13849-1, ISO 13850, ANSI B11.19, Factories Act 1948
- **Excluded — never reference:** IEC 61508, IEC 61800-5-2

### Data Integrity
- **Never invent machine features, specs, or systems** not in raw inputs or RA report.
  Canonical failure: P1 (Accurate Machines) — coolant system was assumed, does not exist.
- Missing data → `**[PLACEHOLDER — description, source, status]**` or Open Action. Never fabricate.
- **Never fabricate standard clause numbers.** If unsure:
  `[INSUFFICIENT EVIDENCE — VERIFY WITH SOURCE STANDARD]`
